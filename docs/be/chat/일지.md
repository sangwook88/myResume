# be/chat 일지

## 현재 상태 요약
fe/chat qa 도출에서 신설(plan-be) + 사람 값 확정. 데이터=대화세션(session_id·턴·Citation, TTL 1일) + 기능 3개(답변생성·제안질문생성·세션이력관리). 코퍼스는 be/point·be/project 참조(소유 아님). 비즈니스 값 충족 — 근거 없으면 답 안 함("근거 없어 답할 수 없음", 환각 방지), 타임아웃 30초, TTL sliding(마지막 활동+1일), load-all은 v1 예산 내 가정(초과=v3 RAG 신호), 맥락 제안질문 3개. 남은 건 패턴(TS/DM)·세션 스토어·LLM 프레임워크 — 전부 arch.

**v4 확장(plan-be→distill):** ① 코퍼스 소스를 공개 get_published → be/point **챗봇컨텍스트조회**(visible+invidence 합집합)로 교체 — 각 Evidence 토큰(`[[E##]]`) 밑에 invidence(detail·code) 부착, 인용 계약 불변. ② **프롬프트 캐싱 정상화** — 안정 프리픽스 요건 고정: 코퍼스 고정 정준 순서(진입 맥락 재배치 제거)→캐시 브레이크포인트→가변 꼬리(진입 맥락 포인터·tone·질문). 캐시 실측(stream_usage로 cache_read 로깅). distill로 답변생성·데이터 본문의 결정이력·현재 결함→수정 diff를 걷어내고 요건 문장만 남김. **남은 슬롯 사람 확정(plan-be):** 캐싱 TTL=**1h**(포폴 챗봇은 방문 간격이 길어 5분 기본이면 방문자마다 미스). **잔여 슬롯 0(정책)** → arch로 진행 가능. **메커니즘(cache_control 배치·1h용 beta 헤더·langchain 배선)은 arch 몫.**

## 이력
### 2026-07-12 — v4 캐싱 TTL 값 확정 (plan-be)
- **결정(사람):** 프롬프트 캐싱 TTL=**1h**(기본 5분 대신). 포폴 챗봇은 방문자 간 간격이 길어 5분 TTL이면 프리픽스 캐시가 방문마다 만료·재생성 → 1h로 유지해 미스·비용 절감.
- **왜:** 트래픽이 뜸한 단일 포폴 챗봇 특성상 재사용 확률이 TTL 길이에 크게 좌우됨. 1h write 비용은 재사용으로 상쇄.
- **영향:** be/chat v4 정책 슬롯 0. 1h TTL용 beta 헤더·cache_control 배치·langchain 배선은 arch. RAG(top-K) 경로는 프리픽스 불안정이라 캐싱 범위 밖(v3 게이트 유지).

### 2026-06-29 — be/chat 신설 (FE-first 도출)
- **결정:** fe/chat qa가 부른 호출(답변 생성·맥락 제안질문·세션 이력)에서 기능 3개 도출. 소유 데이터=대화세션(session_id 키잉, TTL 1일 만료형). 코퍼스는 be/point(published 본문+Evidence)·be/project(표지) 참조로 load-all(RAG 아님).
- **왜:** 챗봇 이력은 be/chat 고유 데이터(세션 쿠키+서버+TTL, localStorage 폐기 결정). 근거 인용은 be/point Evidence 재사용(단일 소유 유지).
- **영향:** HOME 참조 그래프 be/chat→be/point·be/project 유효. 세션 스토어·LLM 프레임워크(LangChain 세션 메모리 등)는 arch에서 확정.

### 2026-06-29 — 값 확정 (사람 결정)
- **결정:** 근거 없으면 답 안 함("근거 없어 답할 수 없음", 일반지식 추측 금지) / 응답 타임아웃 30초 / 세션 TTL sliding(마지막 활동+1일) / load-all은 v1 코퍼스가 예산 내라 가정(초과 시 RAG=v3 신호) / 맥락 제안질문 3개(핵심 섹션 기반).
- **왜:** 근거기반 신뢰가 제품 차별점이라 환각 방지 최우선. 나머지는 익명 웹 챗봇 표준 + 로드맵(load-all=v1) 정합.
- **영향:** be/chat 비즈니스 슬롯 전부 충족 → distill 가능. 세션 스토어 구현·LLM 스택·패턴은 arch.

### 2026-06-29 — arch 확정: TS + Sonnet 5 + LangChain/Redis
- **결정:** 패턴 = TS(트랜잭션 스크립트). LLM = Claude API `claude-sonnet-5` 스트리밍 + **프롬프트 캐싱**(load-all 코퍼스 prefix 캐싱으로 비용↓). 오케스트레이션 = LangChain(Python), 세션 이력 = Redis(sliding TTL 1일).
- **왜:** load-all+근거 인용+세션은 LLM·스토어 오케스트레이션이라 절차적 서비스가 맞음. Sonnet 5는 Opus급 품질에 저렴·빠름(서빙 호출량 유리). 캐싱이 load-all 비용 약점을 메움.

### 2026-06-29 — distill 가지치기
- **결정:** 데이터 `expiresAt` 표기를 sliding(마지막 활동+1일)으로 정정(기능과 불일치 해소), 답변생성 예외의 "근거 없음" 중복 제거(처리에 이미 정의).
- **왜:** 핵심 의미 보존하며 불일치·중복 제거(slim-agent).
- **영향:** 의미 불변. 남은 슬롯은 패턴(arch)뿐.

### 2026-07-12 — v4 하이브리드 코퍼스 + 캐싱 정상화 (plan-be)
- **결정:** (1) 답변생성 코퍼스를 be/point 챗봇컨텍스트조회(visible+invidence 합집합)로 읽어 각 Evidence 밑 invidence(디테일·코드)를 맥락에 싣는다. Citation은 Evidence 재사용(invidence는 인용 대상 아님). (2) 프롬프트 캐싱 정상화 — 프리픽스 안정성을 요건으로 못박음: 고정 지시문→**정준 순서 코퍼스**(진입 맥락 재배치 금지)→캐시 브레이크포인트→가변 꼬리(진입 맥락 짧은 포인터·tone·질문).
- **왜(진단, 코드 기준):** ① `build_corpus`가 진입 맥락 포인트를 코퍼스 맨 앞에 재배치 → 방문자 진입점마다 프리픽스 상이(대량 캐시 미스). ② `_ANSWER_SYSTEM`이 `{tone}`(technical↔hr)을 코퍼스 위에 삽입 → 모드 전환 시 전량 미스. ③ `ChatAnthropic(streaming=True)`에 `stream_usage` 미설정 → cache_read 관측 불가로 검증조차 안 됨. → 셋 다 프리픽스를 흔들거나 관측을 막는 결함.
- **영향:** 참조 그래프 무변(be/chat→be/point 유효, 접근자만 챗봇 전용으로 교체). invidence로 코퍼스가 커질수록 캐싱 이득↑. TTL 값·cache_control 배치·beta 헤더·langchain 배선은 arch. RAG(top-K) 경로는 프리픽스 불안정이라 캐싱 범위 밖(v3 게이트 유지).
- **distill(2026-07-12):** 위 v4 내용을 답변생성·데이터 본문에 인라인으로 덧댄 상태였던 걸 가지치기 — 두 `### v4` 절의 "교체(공개→챗봇전용)" 서술·"현재 결함(확정)→수정" diff·진단 메타를 본문에서 걷어내 이 항목으로 이송, 요건/규칙 문장만 남김. 캐싱 절은 `### 프롬프트 캐싱(프리픽스 안정성)`으로 통합. 기존 pre-v4 규칙 "맥락 있으면 우선 컨텍스트"는 v4의 "재배치 금지·꼬리 포인터"로 정정(불일치 해소). 의미 불변, 남은 슬롯=TTL뿐.
