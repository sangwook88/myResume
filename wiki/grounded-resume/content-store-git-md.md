## 제목·요약
포트폴리오 콘텐츠(프로젝트 표지·포인트)를 관계형 DB가 아니라 git 마크다운 위키(`wiki/<project>/*.md`)에 저장하기로 했다. 이 선택은 배포 모델을 "각자 레포를 포크해 셀프호스팅"으로 고정한다 — 클론하면 곧 배포 단위가 된다.

## 배경
근거기반 포트폴리오는 채용자가 published 위키를 둘러보고 챗봇에 묻는 제품이다. 콘텐츠를 어디에·어떻게 저장할지가 배포·저작·근거 모델을 모두 좌우한다.

## 문제
콘텐츠를 관계형 DB에 넣으면 CRUD·마이그레이션·계정이 필요해지고, 배포마다 DB를 프로비저닝해야 한다. 반면 이 제품의 근거는 "git 커밋"이라, 콘텐츠까지 git에 두면 근거와 저장소가 한 몸이 된다.

## 고려한 옵션
| 옵션 | 장점 | 단점 | 채택 |
|---|---|---|---|
| 관계형 DB (SaaS·멀티테넌트) | 계정·다중 사용자·권한 | v1은 계정 없음 → 과설계 / 프로비저닝·운영 부담 | X |
| BaaS(Insforge 류) | 빠른 셋업·pgvector | 포크마다 BaaS 계정 필요 → "클론하면 끝" 강점 상실 / 백엔드 실력 은폐 | X |
| git 마크다운 위키 | 근거(커밋)와 정합 · 버전관리 · 프로비저닝 0 · 포크=배포 | 멀티테넌트 SaaS엔 부적합 | O |

## 결정과 근거
콘텐츠를 git 마크다운으로 두고, 배포는 "각자 포크해 셀프호스팅"(모델 A)으로 확정했다. 근거: 포크가 곧 배포 단위라 DB 프로비저닝이 0이고(클론 → `wiki/` 채움 → 배포), 근거=git 커밋과 저장소가 정합하며, 저작을 로컬 Claude Code로 무과금 수행할 수 있다. DB(Auth·RLS·pgvector)가 정당해지는 건 오직 한 서비스에 여러 명이 가입하는 멀티테넌트 SaaS(모델 B)로 피벗할 때뿐이고, 그건 roadmap 레벨 재설계라 v1 범위 밖이다.

## 실행
- `2e1024f`: v1 스코프를 "수동 저작 + 근거 강제 + load-all 챗봇"으로 재확정 — 자동 git분석·RAG·Wiki저작엔진을 v3로 미루고 경량 발행 토글 채택, 저작을 로컬/구독 도구로 분리.
- `c7f0989`: ARCHITECTURE 확정 — 저장소를 "Redis(세션) + git 마크다운(콘텐츠), 관계형 DB 없음"으로 명문화하고 콘텐츠 서빙을 Python API 단일 소스로.

## 결과
콘텐츠가 파일이라 포크가 배포 단위가 됐다. DB 스키마·마이그레이션·시드 없이 "클론 → 위키 채움 → 배포"로 끝나고, 근거(커밋)와 콘텐츠가 같은 git 이력에 산다.

## 회고
저장소 선택이 곧 배포·비즈니스 모델 선택이었다. "포폴이라 DB 없으면 맛없다"는 유혹이 있었지만, 이 제품의 진짜 특징은 저장소가 아니라 근거기반 챗봇이고, git-md는 포크형 배포에선 단점이 아니라 강점이었다. DB는 필요해질 때(SaaS 피벗) 넣으면 된다는 YAGNI 판단.
