## 거시 목표

### 문제·가치·경험
- **문제**: 채용자는 개발자의 실제 역량(특히 *판단력*)을 짧은 시간에 정확히 평가하기 어렵다. 정적 포트폴리오는 "무엇을 했다"만 보여주고, 일반 AI 포폴 챗봇은 환각·근거 부족으로 신뢰받지 못한다. *(근거: 리서치 §1.3 채용자 페인 P1·P4·P6)*
- **가치**: 개발자가 실제로 한 작업(git 히스토리 + 인프라)에 **접지된 근거(커밋/PR)로 "왜 그렇게 결정했는가"까지** 답해, 채용자가 신뢰할 수 있는 평가 재료를 준다. *(근거: 리서치 §1.2 공백 A·B·C — 시장에 없는 차별점)*
- **경험**: 채용자가 **읽힌 포폴을 둘러보다가**(렌더된 위키) **궁금한 지점에서 챗봇에 묻는** 하이브리드. 답변의 근거는 각주·펜첼형(접기)으로 노출 — 비기술 채용자에겐 깔끔하게, 기술 채용자는 펼쳐 확인.

### 대상 사용자
- **기술 채용자**(개발팀장·시니어·CTO)와 **비기술 HR/리크루터** 둘 다. **명시 모드 토글**로 눈높이 전환(예: "HR 도움" / "기술 심원").

## 핵심 기능 목록 (성분 단위, 값은 슬롯)

### BE 측 (데이터 + 기능)
- **Git 분석 파이프라인** — 2-Pass(① `git log --oneline` 전체로 고가치 커밋 선별 → ② 선택 커밋만 diff 조회) + 인프라 파일(CI/CD·Docker·migration) 분석 → `raw/<project>/`에 초안. 증분 처리(마지막 분석 해시 이후 신규 커밋만). 고가치 선별 기준·증분 트리거 방식 *[입력 필요]*.
- **Wiki 저작·갱신 엔진** (Wiki Agent) — `raw/` 읽고 `wiki/<project>/` 갱신. 2계층 구조(프로젝트 index + 포폴 포인트 문서). 갱신 전략(전체 재작성 vs 섹션 패치) *[입력 필요]*.
- **포폴 포인트 데이터 모델** — STAR+ADR 하이브리드 9섹션 + 프론트매터(id·title·project·status·tags·commits·updated) + 옵션 비교 표 고정 컬럼. *(§포폴-목차-설계에서 확정)*
- **HITL 승인 상태머신** — `draft → approved`. 개발자 검토·편집이 곧 승인. 챗봇은 `approved`만 인용.
- **챗봇 응답 엔진** — `approved` 위키를 컨텍스트로 질문 응답 + Evidence(커밋/PR) 인용. 위키 합계가 컨텍스트 예산 이내면 load-all(Stage 0). 활성화 임계 비율 *[입력 필요]*.
- **검색/서빙 레이어(성장 사다리)** — Stage 0 load-all → Stage 1 메타필터+dense+small-to-big → Stage 2 하이브리드 → Stage 3 reranker. *(§검색/서빙에서 방향 확정)*

### FE 측 (플로우 + 표현)
- **채용자 둘러보기 화면** — 렌더된 위키(프로젝트 index → 포폴 포인트 문서)를 HTML로 노출. `approved`만 보임.
- **챗봇 UI (하이브리드)** — 둘러보다 궁금한 지점에서 질문. 답변 + 근거.
- **모드 토글** — 기술/비기술(HR) 명시 전환. 답변 깊이·용어가 그에 맞춰 바뀜.
- **Evidence 노출(각주/펜첼형)** — 답변은 자연스럽게 읽히고, 근거는 각주 번호·"근거 보기" 접기로.
- **개발자 검토·승인 UI** — git 분석 초안(포폴 포인트 후보)을 개발자가 검토·편집·승인(HITL). 🤖/✍️ 출처 표기 추적.

### 오케스트레이션(공통)
- **Orchestrator** — Git Agent → Wiki Agent → Chatbot 조율. 트리거 방식(자동 watcher vs CLI 수동) *[입력 필요]* — 리서치상 자동 파일-드랍은 외부 watcher 필요(복잡).

## 리서치 근거 요약
- 조사한 모든 포폴 챗봇은 "무엇을 했다"만 답함 — **트레이드오프(왜) + 커밋/PR 인용 + git→HITL 루프**가 시장 공백(§1.2). 우리 설계가 정면으로 메움.
- 신뢰가 핵심 축: 채용자 54% AI 생성물 불신, NotebookLM 소스 접지로 환각 ~40%→~13%(§1.4 H1).
- 기술 제약: Context Rot — 200K 윈도우도 **~50K 토큰부터 성능 저하** → 위키를 작게 유지(§3.1). load-all 임계치는 *근거 있는 슬롯*.
- MVP 현실적: 로컬 blobless clone + Claude(캐싱/배치) + Vercel Hobby + load-all이면 임베딩·벡터DB 없이 시작 가능(§4.5).
- 전문: [portfolio-agent-research.md](portfolio-agent-research.md)

## 엣지케이스 체크리스트 (사람이 채울 분기)
- **빈/소량 git** — 커밋이 거의 없거나 비공개 repo만 있을 때 포폴 생성 동작? *[입력 필요]*
- **대량 커밋** — 변경 300파일 초과 커밋 diff 페이지네이션/타임아웃 처리(리서치 §2.1). *[입력 필요]*
- **위키가 컨텍스트 예산 초과** — load-all 임계 넘으면 Stage 1로 자동 전환하는 기준. *[입력 필요]*
- **승인 안 된 초안만 있는 프로젝트** — 챗봇이 "아직 미확인"을 어떻게 응대? *[입력 필요]*
- **모드 토글 미선택(기본값)** — 기술/비기술 중 기본 모드. *[입력 필요]*
- **근거 없는 질문** — 위키에 답이 없을 때 챗봇 응대(환각 방지). *[입력 필요]*
- **답변 신뢰도 표기** — draft 인용 금지/배지 처리. *[입력 필요]*

## 안 할 것 (YAGNI — 제품 비전에서 제외)
- **음성/아바타 등 멀티모달** — 핵심(근거 기반 Q&A)과 무관. (source-persona식 TTS 트윈 — 제외)
- **다중 개발자/공개 SaaS** — 여러 사람이 각자 포폴 올리는 서비스화. 본인 1명 포폴이 비전.

> 참고: **임베딩/벡터 검색**과 **자동 파일-드랍 트리거**는 "안 함"이 아니라 *뒤 버전으로 미룸* 후보 — 버전 배치는 [roadmap](../../.claude/skills/roadmap/SKILL.md)에서 확정.
