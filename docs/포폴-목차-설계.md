# 포트폴리오 에이전트 — 포폴 목차/문서 템플릿 설계

> 저장 일시: 2026-06-07
> 상태: 설계 합의 완료 (브레인스토밍 결과)
> 관련 문서: [프로토타입_기획.md](프로토타입_기획.md)

---

## 1. 목적

포트폴리오 에이전트가 **하나의 프로젝트 + 개발자가 한 일 + 관련 git** 을 입력받아,
"무엇이 문제였고 / 무엇을 해야 했고 / 어떤 옵션이 있었고 / 어떤 결정을 했고 / 결과가 어땠는지"
를 일관된 **목차(템플릿)** 로 정리하게 한다.

이 문서는 그 **목차/문서 템플릿 자체**를 정의한다. (에이전트 구현 방식이 아니라 산출물 구조)

---

## 2. 합의된 전제 (브레인스토밍 결정사항)

| 항목 | 결정 |
|---|---|
| **단위** | 포트폴리오 프로젝트 1개 → 목차 생성 → 목차 항목(내용)별 문서 1개씩 → LLM wiki → 챗봇 |
| **1차 독자** | 챗봇이 읽는 구조화 wiki 우선. 동시에 HTML로 사람에게도 노출 가능해야 함 |
| **옵션·결정·이유 출처** | AI 초안 + 개발자 확인/편집 (Human-in-the-Loop) |
| **서술 프레임워크** | **하이브리드(C)** = STAR 가독성 + ADR 판단 기록 |

### 프레임워크 선택 근거
- **A. STAR**: 읽기 쉽지만 "옵션 비교/트레이드오프"라는 엔지니어링 판단력을 담을 칸이 약함 → 기각
- **B. ADR**: 결정의 근거 기록엔 최강이나 건조해 포폴 스토리로는 딱딱함 → 기각
- **C. 하이브리드 (채택)**: STAR로 읽히면서 "옵션/결정/근거"를 별도 섹션으로 살려 판단력을 드러냄.
  챗봇이 "왜 X 대신 Y를 썼나요?"에 정확히 답하기에도 최적. HTML 노출 시 스토리로도 읽힘.

## 3. 2계층 구조

```
wiki/<project>/
  index.md            ← 1계층: 프로젝트 인덱스(카탈로그)
  <point-1>.md        ← 2계층: 포폴 포인트 문서 (목차 항목 1개 = 문서 1개)
  <point-2>.md
  ...
```

---

## 4. 1계층 — 프로젝트 인덱스 문서 (`wiki/<project>/index.md`)

채용자가 "이 프로젝트 뭐예요?"라고 물을 때 챗봇이 먼저 읽는 카탈로그.

1. **프로젝트 한 줄 요약** — 무엇을, 왜, 누구를 위해
2. **나의 역할 & 기간 & 팀 규모** — 기여 범위 명시
3. **기술 스택** — 언어/프레임워크/인프라 (git 자동 추출)
4. **아키텍처 개요** — 시스템 구성 한눈에 (다이어그램/설명)
5. **핵심 성과 3줄** — 임팩트 위주 하이라이트
6. **포폴 포인트 목록(목차)** — 2계층 문서들로 링크 + 한 줄 설명

---

## 5. 2계층 — 포폴 포인트 문서 (`wiki/<project>/<point>.md`)

목차 항목 하나당 이 템플릿 하나. 각 섹션의 **출처** 표기:
- 🤖 = git에서 자동 초안
- ✍️ = 개발자 확인/입력 필요 (HITL)

1. **제목 & 한 줄 요약** 🤖→✍️ — 예: "결제 모듈 동시성 버그를 분산락으로 해결"
2. **배경 / 맥락** 🤖 — 어떤 프로젝트의 어느 지점에서 생긴 일인지
3. **문제 / 해야 했던 것** 🤖→✍️ — 풀어야 했던 문제, 요구사항, 제약(기한·트래픽·레거시 등)
4. **고려한 옵션** ✍️(AI 초안) — 옵션 A/B/C 각각의 장단점·트레이드오프 표
5. **결정과 근거** ✍️ — 무엇을 골랐고 **왜**. 기각한 옵션을 왜 버렸는지 포함
6. **실행 / 한 일** 🤖 — 실제 구현·변경 내용 (커밋·PR·diff 근거 링크)
7. **결과 / 임팩트** ✍️ — 정량(지표 개선, %, ms, 비용) + 정성(안정성 등)
8. **회고 / 배운 점** ✍️ — 다시 한다면, 한계, 남은 빚
9. **근거(Evidence)** 🤖 — 관련 커밋 해시·PR·파일 경로. 챗봇 답변의 출처 + 신뢰도 ↑

---

## 6. 설계 포인트

- **4·5번(옵션·결정)이 이 시스템의 차별점.**
  보통 포폴 챗봇은 "뭘 했다"만 답하지만, 이건 "왜 그렇게 했냐"에 답함 = 시니어 판단력 어필.
- **9번 Evidence**는 RAG 없이도 챗봇이 근거를 댈 수 있게 하고 환각을 줄임
  (기획문서의 `git_analysis.md`와 연결).
- **출처 표기(🤖/✍️)를 메타데이터로 남기면**, HITL 단계에서
  "아직 개발자 확인 안 된 항목"을 추적할 수 있음.

## 7. 문서 포맷 상세

구조화된 **마크다운**으로 작성 → 챗봇이 파싱 쉽고, 렌더링하면 HTML로 보기 좋음.

### 7.1 프론트매터 스키마 (균형형)

각 포폴 포인트 문서 상단에 YAML 프론트매터를 둔다. 본문 이모지(🤖/✍️)만으로는
기계가 필터링/추적을 못 하므로, 챗봇·에이전트가 읽을 메타데이터를 구조화한다.

```yaml
---
id: payment-distributed-lock          # 파일명·링크용 식별자 (slug)
title: 결제 동시성 버그를 분산락으로 해결
project: shopping-mall
status: draft                         # draft → approved (§7.2)
tags: [concurrency, redis, payment]   # 검색·필터·인덱스 그룹핑용
commits: a1b2c3d..e4f5g6h             # 근거 커밋 범위 (증분 분석·추적)
updated: 2026-06-07
---
```

### 7.2 status 상태머신

- `draft` — AI가 채운 초안. 챗봇은 인용하지 않음(또는 "미확인 초안"으로만 취급).
- `approved` — 개발자가 검토/편집을 마친 상태. 챗봇이 자신 있게 인용.
- **전이:** 개발자의 검토·편집 행위가 곧 승인. Wiki Agent가 HITL 반영 시
  `draft → approved`로 자동 승격한다. (중간 `reviewed` 상태는 두지 않음)

### 7.3 인덱스 ↔ 포인트 링크 규칙

- 파일명 = `wiki/<project>/<id>.md` (프론트매터 `id` 그대로 사용).
- `index.md`의 "포폴 포인트 목록"은 **Wiki Agent가 폴더를 스캔해 자동 생성**한다.
  각 `*.md`의 프론트매터(`title`/`status`/`tags`)를 읽어 목록을 구성 →
  링크 깨짐·수동 관리 부담 없음, 새 문서는 자동 등장.
- 챗봇/HTML 노출용 인덱스에는 `status: approved`만 노출.
  개발자용 뷰에서는 `draft`도 상태 배지와 함께 표시 가능.

### 7.4 옵션 비교 표 표준 컬럼

4번(고려한 옵션)은 아래 고정 컬럼의 표로 작성한다. 컬럼을 고정해 AI 초안 품질과
챗봇 답변 일관성을 확보하고, "왜 기각했는가(채택 컬럼)"까지 한눈에 보이게 한다.

| 옵션 | 장점 | 단점 | 비용·리스크 | 채택 |
|---|---|---|---|---|
| DB 비관적락 | 추가 인프라✖ | 충돌시 재시도 | 낮음 | ✖ |
| Redis 분산락 | 빠름, 단순 | Redis 의존 | 중 | ✔ |
| Kafka 직렬화 | 확장성 | 과투자 | 높음 | ✖ |

## 8. 검색/서빙 레이어 (RAG 기법을 LLM Wiki에 적용)

### 8.1 핵심 재구성: 위키 = 저작, RAG = 서빙

LLM Wiki("전체를 컨텍스트에")와 RAG("질문마다 검색")는 충돌이 아니라 **작동 시점이 다르다.**
- **위키** = 지식이 정제·축적되는 저작 레이어 (raw → HITL → approved 문서)
- **RAG 검색** = 질문 시점에 *어떤 위키를 컨텍스트에 올릴지* 고르는 서빙 레이어

포트폴리오가 작으면 approved 전부를 컨텍스트에 넣으면 된다(=순수 LLM Wiki).
검색은 문서가 늘어 컨텍스트 예산을 넘을 때 "무엇을 고를까"를 담당한다.
그리고 §7의 구조(프론트매터·섹션·옵션표)가 각 RAG 레이어를 더 싸고 정확하게 만든다.

### 8.2 검색 레이어 ↔ 위키 구조 매핑

| RAG 레이어 | 위키에서의 적용 | 위키 이점 |
|---|---|---|
| **L1 문서 필터링** | `status:approved`만 검색 + 프론트매터(`project`/`tags`) 메타 사전필터 | 휴리스틱 노이즈 제거가 아니라 구조화 필드 필터 → 신뢰도 ↑ |
| **L2 청킹/Contextual** | 섹션이 곧 청크 경계. 청크 앞에 `[project·title·섹션]` 접두어 = Contextual prefix를 LLM 호출 없이 확보 | Contextual Retrieval의 비싼 부분을 구조가 대체 |
| **L3 하이브리드** | BM25(기술명·고유명사) + dense(의미), RRF 결합. `tags`/`tech` 필드 가중 | 정규화된 필드로 BM25 정밀도 ↑ |
| **L4 Reranker** | top-K 섹션을 cross-encoder 재정렬 | 섹션이 자기완결적이라 점수 깨끗 |

### 8.3 Small-to-big (LLM Wiki 정신 유지)

검색은 *섹션 청크* 단위로 하되, 컨텍스트엔 **그 청크의 부모 포폴 포인트 문서 전체**를 올린다.
"단위마다 전체 맥락을 본다"는 LLM Wiki 정신을 지키면서, *어떤 단위*를 고를지만 검색에 맡긴다.
답변엔 §5의 Evidence(커밋/PR)를 출처로 인용 → NotebookLM식 근거 제시.

### 8.4 성장 사다리 (4레이어를 실용 순서로) — **v1 = Stage 1**

- **Stage 0 — Load-all (검색 없음):** approved 전부를 컨텍스트에. 합계가 예산 안이면 최선.
  → v1에 "문서 적으면 전부 로드"하는 지름길로 내장.
- **Stage 1 — 메타필터 + dense + Small-to-big (← v1 목표):**
  ①`status:approved`+`project`/`tags` 필터 → ②dense 임베딩 top-K 섹션 → ③부모 문서 통째 로드.
- **Stage 2 — 하이브리드(BM25+dense, RRF):** 기술명·고유명사 정확도 필요해지면 추가.
- **Stage 3 — Reranker + Contextual prefix:** 후보가 많아 정밀 재정렬이 필요하면 추가.

핵심: Stage 1의 골격(필터 → 검색 → small-to-big)만 제대로 잡으면 Stage 2·3은
"검색 단계 안에 모듈을 끼워넣는" 일이라 무리 없이 자란다.

### 8.5 설계 메모 / 결정 필요

- **활성화 임계치:** 전체 approved 토큰 합 ≤ 컨텍스트 예산이면 Stage 0(load-all), 넘으면 Stage 1.
  합계는 인덱스/프론트매터로 싸게 추정. (정확한 임계 비율은 튜닝값)
- **임베딩 모델:** 본문이 **한국어**이므로 다국어/한국어 지원 dense 임베더 필수. (모델 선정은 구현 단계)
- **청크 단위:** §5 템플릿의 섹션 단위. 옵션표는 통째로 하나의 청크.
- `[project·title·섹션]` 접두어는 비용이 거의 없어 v1(Stage 1)부터 붙여도 무방.
