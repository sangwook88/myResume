## 제목·요약
개발 단계에 오케스트레이터(desk)·빌드 진입점(build)·구현자(dev)로 나뉘어 있던 역할을, dev 하나로 통합했다. 빌드 오케스트레이션(참조 그래프 BE→FE wave 편성·빈슬롯 게이트·상태 마감)을 dev가 흡수하고 desk·build를 삭제했다.

## 배경
구현 흐름에 여러 에이전트·스킬이 있었다. desk가 도메인을 분류하고 wave를 편성하는 오케스트레이터였고, build가 구현 진입점, dev가 리프 구현자였다.

## 문제
역할이 중첩됐다. 기획 단계(plan)가 이미 도메인을 FE/BE로 분류해 두는데, desk가 또 분류·편성을 한다 — 분류 두뇌가 둘이다. build 진입점도 dev와 하는 일이 겹쳐, 개발 경로가 불필요하게 복잡했다.

## 고려한 옵션
| 옵션 | 장점 | 단점 | 채택 |
|---|---|---|---|
| 역할 분리 유지 (desk=오케스트레이션, build=진입점, dev=구현) | 각 역할이 작고 단일 | 상류(plan)와 분류 중복 / 진입점 2개 / 경로 복잡 | X |
| dev 단일 두뇌로 통합 | 진입점 하나 / 상류 분류를 그대로 신뢰 | dev 책임이 넓어짐 | O |

## 결정과 근거
dev를 단일 구현 두뇌로 통합했다. 근거: plan 단계가 이미 도메인을 분류해 두므로 별도 분류 두뇌(desk)도, 별도 빌드 진입점(build)도 불필요하다. dev가 빌드 오케스트레이션(HOME 참조 그래프로 BE→FE wave 편성·빈슬롯 게이트·헤드리스 안내·상태 마감)을 흡수하면 개발 경로가 dev 단일 진입으로 단순해진다.

## 실행
- `60f3c69`: 개발 플로우 재설계 — intake(종합 창구)가 문서를 기획/개발로 분배, dev(리프 구현자 → 개발 리드)가 티켓 분해·승인·구현까지, plan은 개발 유발 시 dev 인계 메모.
- `df44472`: `agents/desk.md`·`skills/build/SKILL.md` 삭제, 빌드 오케스트레이션을 dev로 이관, 에이전트 4종·스킬 11종으로 개수 표기 갱신.

## 결과
개발이 dev 단일 진입점으로 단순화됐다. 상류(plan)의 분류를 하류가 중복하지 않아, 같은 일을 두 번 하는 경로가 사라졌다.

## 회고
"역할을 잘게 나누는 것"이 항상 선(善)은 아니다. 상류가 이미 한 일(도메인 분류)을 하류(desk)가 되풀이하면, 분리는 단순함이 아니라 중복·혼선을 만든다. 책임이 겹치는 두 두뇌는 통합하는 편이 낫다는 판단이었다. 내가 만든 컴포넌트를 지우는 결정이라 더 신중했다.
